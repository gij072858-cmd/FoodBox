## 1. 分层与三条纪律

```
   页面 / 组件          成员二 · 三 · 四 写这里
        │
        ▼  只能通过接口调用（不许 import 数据库）
 ┌──────────────────────────────────────────────┐
 │  Repository 接口层（abstract interface class） │  ← 本文冻结的就是这一层
 │  PantryRepository / RecipeRepository          │
 │  ScheduleRepository / ProfileRepository       │
 └──────────────────────────────────────────────┘
        │
        ├── 本地实现：Drift + SQLite        （W2 交付，期1 唯一实现）
        └── 云端实现：Supabase               （期2 v1.1，接口不变、只换实现类）
```

**三条纪律（违反会在 Code Review 里被打回）：**

1. **页面不得直接操作数据库**。想读数据就调 Repository；没有你需要的方法，提接口变更申请。
2. **领域模型不依赖 Drift**。`lib/data/models/` 下的类不能 import `package:drift`，这样期2 换云端实现时上层页面零改动。
3. **表和字段名不得在页面里出现**。禁止 `SELECT`、禁止拼接表名、禁止绕过接口写实现。

## 2. 数据模型（六张表）

### 2.0 总览

| # | 表名 | 领域模型 | 行类型（Drift 生成） | 说明 |
|---|---|---|---|---|
| 1 | `items` | `Item` | `ItemRow` | 食材 / 调料条目 |
| 2 | `recipes` | `Recipe` | `RecipeRow` | 菜式（配方清单以 JSON 内嵌，见 2.7） |
| 3 | `steps` | `Step` | `StepRow` | 菜式步骤（时序引擎的输入） |
| 4 | `schedule_items` | `ScheduleItem` | `ScheduleItemRow` | 时序待做清单 |
| 5 | `records` | `CookRecord` | `RecordRow` | 做菜记录与复盘笔记 |
| 6 | `profiles` | `Profile` | `ProfileRow` | 用户档案与三栏清单（恒 1 行） |

**口径澄清**：总计划第五章 W1 段曾写"五张表"，缺少 `records`。以总计划**第七章**与构想**附录**为准 —— **六张表（含 Record）**，本组按六张表执行。

### 2.1 `items` —— 食材 / 调料条目

| `stored_at` | DATETIME | 可空 | 入库日期 |

**卡片展示口径（Q1-B / Q2-B）**：卡片只显示「名称 + 剩余天数 + 数量」；
剩余天数 = 到期日 − 今天（自然日，未设到期日则为空）。**负数表示已过期**。
临期判定：`0 ≤ 剩余天数 ≤ 3`（预警橙 `#FF9500`）。

| `created_at` | DATETIME | 默认当前时间 | |

**`ingredients` JSON 元素结构**（对应 Dart 类 `RecipeIngredient`）：

```json
{ "name": "番茄", "amount": 2, "unit": "个", "isRequired": true, "isSeasoning": false }
```

- `isRequired`：非必需项缺失**不影响**「可做」判定（阈值只看必需项）；
- `isSeasoning`：区分食材 / 调料，菜式详情页据此分两列展示。

### 2.7 四个技术决策（为什么这么设计）

| 决策 | 选择 | 理由 |
|---|---|---|
| 配方明细是否单独建表 | **不建**，以 JSON 内嵌 `recipes.ingredients` | 保持六张表口径；30–50 道菜式规模下，集合匹配一次性读取即可，无需 JOIN；`RecipeMatcher` 归一匹配只需要名称集合 |
| DateTime 的存储格式 | **ISO-8601 文本**（`build.yaml` 中 `store_date_time_values_as_text: true`） | 默认的整数时间戳读出来是 UTC，跨时区展示会差几小时；文本存储保留时区信息，Dart 侧语义一致 |
| 枚举如何落库 | **存枚举 name 字符串**（`textEnum`） | SQLite 宽松、加值不用迁移；坏值读取时容错为 null 而非抛异常 |
| 领域模型是否直接用 Drift 行类型 | **不直接共用** | 页面不能被数据库类型污染；`local/mappers.dart` 负责互转，期2 换云端只加一份 mapper |

## 3. 跨模块契约（**最重要的一章**）

这四条是"模块之间怎么说话"的唯一约定。**改动这四条必须走第 6 章流程。**

### 3.1 库 → 菜式

| 项 | 约定 |
|---|---|
| 提供方 | 组长（`PantryRepository`）、组长（`RecipeMatcher`） |
| 调用方 | 成员三（菜式页推荐区） |
| 库存流 | `PantryRepository.watchAll({ItemKind? kind}) → Stream<List<Item>>` |
| 匹配算法 | `RecipeMatcher.matchAll(List<Recipe>, List<Item>) → List<RecipeMatch>` |
| 阈值 | 「差一点就能做」= 缺失**必需**项 ≤ **2**（Q6-A），常量 `kAlmostCanCookThreshold` |
| 数量口径 | 期1 只做**存在性匹配**：库存条目只要存在即算命中，「快没了 / 已用完」也算命中，不做数量比较 |
| 名称归一 | 必须经 `AliasTable.normalize`（西红柿 = 番茄）；别名表由组长在 W4 维护 `assets/data/alias_map.json` |
| 排序 | 可做（耗时升序）→ 差一点（缺失数升序）→ 差太多 |
| 交付时点 | W4（组长），成员三 W4 起可依赖 |

### 3.2 菜式 → 时序

| 项 | 约定 |
|---|---|
| 提供方 | 组长（`ScheduleRepository`） |
| 调用方 | 成员三（长按加入时序浮层，构想 2.3.4） |
| 签名 | `ScheduleRepository.add(int recipeId, {int servings = 2}) → Future<void>` |
| 幂等性 | **同一 recipeId 重复调用不得产生重复条目**，已存在时视为更新份数 |
| 取消 | `ScheduleRepository.remove(int recipeId)` |
| 边界 | 成员三**不需要**知道时序怎么排程；只管调 add / remove |

### 3.3 时序 → 库

| 项 | 约定 |
|---|---|
| 提供方 | 组长（`PantryRepository`） |
| 调用方 | 组长（时序执行完成闭环） |
| 签名 | `PantryRepository.consume(int recipeId, {int servings = 2}) → Future<void>` |
| 事务性 | 同一菜式的多条食材扣减必须在**同一事务**内完成 |
| 归零处理 | 数量归零的条目**置灰不删除**：扣减至 0 时置 `items.is_depleted = true`（v1.1 新增字段），由页面提示「已用完，是否移出库 / 加入购物清单」 |
| 触发时机 | 时序流程执行完毕后，与写 `records`、XP 结算同一闭环 |

### 3.4 倒计时组件

| 项 | 约定 |
|---|---|
| 提供方 | **成员四**（`lib/widgets/` 共享区，W3 交付） |
| 调用方 | 成员三（菜式详情步骤分割线）、组长（时序执行页） |
| 签名 | `FbCountDownBar({required Duration duration, VoidCallback? onDone})` |
| 纪律 | 调用方**不得自己重写**倒计时条；有需求变更找成员四 |
| 底层口径 | 统一使用组长提供的 `CountdownController`（`lib/core/countdown.dart`）—— **结束时间戳方案，严禁 Timer 周期计数累加**，这是构想第四章改进 7 定下的技术规范 |

## 6. 冻结声明与变更流程

本文件自 **2026-09-11** 起冻结。变更流程（总计划第七章第 4 条）：

1. **提案**：在群里说明「改什么 + 为什么 + 影响谁」；
2. **裁决**：组长拍板（纯视觉规范类由成员四拍板）；
3. **改文档**：先更新本文件（改版本号、在文末变更记录加一行）；
4. **确认**：受影响模块的负责人回复确认；
5. **改代码**：以上都完成后才能动代码。

> 顺序不能颠倒。**先改文档再改代码**，是防止"代码跟文档对不上"的唯一办法 —— 答辩最常被查的就是这个。
