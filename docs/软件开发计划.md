## 1. 引言

### 1.1 编写目的

明确食匣 FoodBox 项目的目标、范围、团队组织、技术路线、进度安排、质量保障与风险应对，作为项目全过程的管理依据与验收基准。

预期读者：项目组全体成员、课程指导教师、答辩评审。

### 1.2 项目背景

在家做饭的人普遍面临三个具体问题：

1. 冰箱里有什么、还剩多少天，全靠记忆，结果反复买、反复扔；
2. 面对现有食材想不出能做什么菜，最后还是点外卖；
3. 一次做两三道菜时手忙脚乱——汤在炖、锅在烧、菜还没切，顾此失彼。

现有产品多只解决其中一个（记账类管库存、菜谱类管做法），**没有把"库存—菜式—时序"串成一条链路**。食匣的切入点正是这条链路。

### 1.3 术语

| 术语 | 含义 |
|---|---|
| 库 | 用户现有食材与调料的管理模块 |
| 菜式 | 菜谱，含食材清单、用量、步骤、耗时 |
| 时序 | 把多道菜的步骤自动重排成一条可执行的做菜时间线 |
| 倒推 | 由目标开饭时刻反推各步骤开始时刻与"几点开始动手" |
| 期1 / 期2 | 期1 = W1–W8 课程项目（底线目标）；期2 = 发布后长期迭代（追求目标） |

## 2. 项目概述

### 2.1 项目目标（两期结构）

**期1 · 底线目标（W1–W8）**：完成软件工程课程作业。五份课程文档齐全，App 核心链路可演示，通过答辩。

期1 范围 = **核心链路**（库 / 菜式 / 时序含倒推与拖拽 / 我的 XP 体系 / 动态占位）
+ **期1 功能包**：F1 购物清单、F2 份量换算、F3 临期提醒、F4 悬浮计时条、F6 数据导出备份、F12 时令推荐（简易版）、F14 复盘笔记、F8 步骤术语解释。

**期2 · 追求目标（v1.0 发布后）**：做成真正能用、长期维护的产品——上云（Supabase + 账号体系）、社区（动态真实化 + 运营）、体验增强包（深色模式、成就、语音播报等）。

> 期2 规划写入《需求分析》的「远期规划」章节，**展示规划能力而非半成品**。

### 2.2 交付物与核心指标

**三项关键交付（W1 周末里程碑）**：
1. 空壳 App 双端可跑（底部 TabBar + 首页顶部三 Tab 框架）；
2. 《接口约定.md》初版创建并冻结；
3. 本计划书 v1 定稿。

**核心指标（期1 终验）**：

| 维度 | 指标 |
|---|---|
| 核心链路 | 录入食材 → 推荐菜式 → 加入时序 → 排程执行 → 倒计时引导 → 扣减库存 → 打卡记录，全链路无阻断性 bug |
| 初始内容 | 预置食材/调料 200+ 条、官方菜式 30–50 道（步骤带耗时） |
| 双端 | 安卓 App + Windows 桌面端均可运行 |
| 设计还原 | 严格执行《01-食匣详细构想》1.3 设计规范，关键页面达 95% 还原 |
| 文档 | 五份课程文档齐全，且与实际代码一致 |

### 2.3 不做什么（范围边界）

明确排除，避免范围蔓延：

- **不做后端服务**：期1 无服务端，Repository 接口层预留 Supabase 云实现（期2 启用）；
- **不做 AI 智能排程**：排程为确定性规则引擎，对外不使用"AI / 智能最优"表述；
- **不做图像识别食材**：拍照识别列入远期愿景，不纳入两期承诺；
- **不做社区真实功能**：期1 动态仅 UI 占位 + 演示数据；
- **不做深色模式**：F5 明确移入期2（期1 以"组件全部引用 Theme 常量"为其铺路）。

## 3. 团队组织与分工

### 3.1 角色与责任

采用**模块纵向切分 + 混合式"辅"责任**：每人主攻一个模块，同时承担一项横向职责。

| 角色 | 模块责任 | 横向责任 |
|---|---|---|
| **组长** | 架构 + 数据层 + 时序模块 | 统筹排期、接口裁决、代码整合、GitHub 管理、课程文档主笔、答辩材料 |
| **成员二** | 库模块（食材 / 调料） | 食材基础数据整理、库相关测试用例 |
| **成员三** | 菜式模块 | 官方菜式内容录入、菜式相关测试用例 |
| **成员四** | 动态占位 + 我的 + 公共 UI 组件库 | UI 设计规范守护与走查、测试文档主笔 |

**工作量说明**：组长任务量最大（架构 + 算法 + 整合 + 答辩）；成员四页面量较少但承担公共组件与测试文档，总负荷持平。

### 3.2 决策机制

| 分歧类型 | 裁决人 | 留痕方式 |
|---|---|---|
| 技术、接口、排期 | 组长 | Issue / 提交说明 / `docs/` 更新 |
| 纯视觉规范 | 成员四（设计规范守护者） | 同上 |
| 任务认领 | 意愿优先、模块延续为辅；无人认领由组长按剩余负荷指派 | 看板卡片 |

### 3.3 协作与沟通机制（摘要）

- **渠道分层**：微信群（日常问答，当天回）、GitHub Issues / 提交记录（正式决定必须留痕，24 小时内回）、仓库 `docs/`（唯一事实源）；
- **口头决定的时效**：群里说定的技术决定，**24 小时内必须落成文字**，否则不算数；
- **会议节奏**：周五组会（里程碑验收 + 风险检查 + 任务认领）、W1 需求确认会、W3 算法评审（并入组会）；
- **任务同步**：GitHub Projects 看板四列（待办 / 进行中 / 待评审 / 已完成），组会只看看板，不逐人口头汇报；
- **文档纪律**：`docs/` 是唯一事实源，**禁止用聊天文件传播"最新版"**。

## 4. 技术方案

### 4.1 技术选型

| 决策项 | 定案 | 理由 |
|---|---|---|
| 框架 | **Flutter（Dart）** | 一套代码产出安卓 + Windows 双端；声明式 UI 适合实现精致设计；团队统一学一门语言 |
| 状态管理 | **Riverpod** | 编译期安全、测试友好、社区主流 |
| 本地数据库 | **Drift（SQLite）** | 类型安全的 SQL 封装，支持 Stream 监听，适配本项目的结构化数据 |
| 后端 | **期1 无服务端**，Repository 接口层隔离数据访问，预留 Supabase 云实现 | 8 周内规避后端风险，架构不留债 |
| 路由 | **go_router** | 声明式路由，双端一致；分支导航壳保证各 Tab 独立导航栈 |
| 扫码 | `mobile_scanner`（安卓端）；电脑端降级为手动输入条码 | 双端能力差异已在构想 Q11-B 确认 |
| 倒计时 | **结束时间戳方案**：记录结束时刻，每帧按时间差渲染；本地通知兜底 | 从根上解决后台挂起恢复与多倒计时并行的漂移问题 |
| 图片 | 真实高清图优先 + 缺图 AI 生成统一风格兜底 + 用户自拍；资源目录可整体替换 | 版式与图解耦，图库扩充不动版式 |

### 4.2 系统架构

```
        表现层  features/（各模块页面）+ widgets/（公共组件库）
                                    │
        领域层  data/models/（领域模型，不依赖数据库）
                                    │
        接口层  data/repositories/（Repository 抽象接口）   ← 期2 替换实现的接缝
                          │                      │
        数据层  local/（Drift + SQLite）    supabase/（期2 v1.1）
```

**三条架构纪律**（《接口约定.md》第 1 章）：

1. 页面不得直接操作数据库，只能调 Repository 接口；
2. 领域模型不依赖 Drift，保证期2 换云端时上层零改动；
3. 倒计时一律基于 `CountdownController`，严禁 Timer 周期计数累加。

### 4.3 代码结构约定（mono-repo）

```
FoodBox/
├── app/                    # Flutter 工程
│   ├── lib/
│   │   ├── core/           # ★共享区：主题常量、路由、倒计时工具、依赖注入
│   │   ├── data/           # ★共享区：Drift 数据库、领域模型、Repository 接口与实现
│   │   ├── features/       # 各模块自留地
│   │   │   ├── pantry/     #   库（成员二）
│   │   │   ├── recipe/     #   菜式（成员三）
│   │   │   ├── schedule/   #   时序（组长）
│   │   │   ├── feed/       #   动态占位（成员四）
│   │   │   ├── profile/    #   我的（成员四）
│   │   │   ├── home/       #   首页框架 + 搜索（组长）
│   │   │   └── shell/      #   底部导航壳（组长）
│   │   └── widgets/        # ★共享区：公共组件库（成员四 owner）
│   ├── assets/             # 预置数据 JSON、图片素材
│   └── test/               # 单元测试 / 组件测试
└── docs/                   # 全部文档（唯一事实源）
```

★ 标记为**共享区**：改动共享区文件必须在提交说明里加 `[shared]` 并在群里同步。

### 5.2 关键路径

```
W1 地基 ──▶ W2 数据层可用 ──▶ W3 库可用 ──▶ W4 推荐算法 ──▶ W5 引擎编码 ──▶ W6 核心链路全通 ──▶ W7 冻结 ──▶ W8 答辩
```

- **风险最高的一周**：W6（时序执行页 + 拖拽校验 + 悬浮条 + 闭环）；
- **不可压缩项**：开饭时间倒推、步骤拖拽（Q7-A / Q8-A 已确认期1 必做，不作为降级项）。

## 6. 质量保证

### 6.1 质量三关

| 关 | 时机 | 责任人 | 标准 |
|---|---|---|---|
| **Code Review 关** | 随时 | 组长 Review（直推 dev 后随查） | 能跑、符合接口约定、无明显 UI 违规 |
| **走查关** | W3 / W7 | 成员四（对照设计规范逐页走查） | 问题录为 issue，限期清零 |
| **验收关** | 每周末 | 组长主持 | 对照当周里程碑逐条演示确认，**录屏存档** |

### 6.2 工程标准

- **静态检查**：每次推送前必须跑 `dart analyze`（无 error；路径含中文时 `flutter analyze` 会崩）、`flutter test`（全绿）、`dart format .`；
- **测试覆盖**：数据层（漂移表与转换器）与新算法（推荐匹配、规则引擎）必须有单元测试；
- **接口纪律**：跨模块调用只走《接口约定.md》第 3 章的契约，变更须走流程；
- **设计纪律**：禁止硬编码色值 / 圆角 / 字号，一律引用 `lib/core/theme.dart`。

### 6.3 v1.0 验收标准

- **功能**：核心链路五环节（录食材 → 推荐 → 排程 → 执行 → 扣库存）无阻断性 bug；
- **流畅**：列表滚动与转场无明显掉帧（目标 60fps，演示机实测）；
- **设计**：走查 issue 清零，库 / 菜式详情 / 时序执行三个关键页面达规范 95% 还原；
- **文档**：五份课程文档与代码一致。

## 7. 风险管理

| 风险 | 概率 | 影响 | 应对预案 |
|---|---|---|---|
| 时序算法延期 | 中 | 核心卖点受损 | 降级 L1：F12 简化为静态标签页、F1 简化为纯文本清单；降级 L2：规则引擎只保「安全插入 + 等待并行」两条核心规则，倒推改为顺排展示（保留 UI 入口）。**保底：UI 完整 + 核心规则正确，绝不砍 UI** |
| 进度整体落后 ≥1 周 | 中 | 演示不完整 | 启动降级链：动态占位减演示数据 → F12 简化 → F1 简化 → F6 简化为仅导出无导入。**库 + 菜式 + 时序核心链路在任何降级下都必须保住** |
| 成员掉线 / 失联 | 低 | 任务悬空 | 每周五里程碑录屏即进度存档；掉线超 3 天，组长按剩余周重分任务，已完成部分直接接手 |
| 扫码在演示机上不工作 | 中 | 演示卡壳 | 演示路径永远以「手动录入」为主、扫码为加分项；现场备备用机与离线数据包 |
| 菜式数据录入量不足 | 低 | 内容单薄 | 底线 25 道（W5 检查点），不足时组长协调全组周末集中补录 |
| 高清图收集不足 | 中 | 观感下降 | W4 检查配图覆盖率；不足部分上调 AI 生成兜底比例，保证 W5 前每道菜与常用食材有图 |

## 8. 配置管理与协作规范

### 8.1 分支模型

| 分支 | 规则 |
|---|---|
| `main` | 受保护，仅组长合并；每个里程碑打 tag（v0.1 … v1.0） |
| `dev` | 集成分支，**全组直接 push（免 PR）**，每晚保持可运行状态 |
| `feature/<模块>-<简述>` | 个人功能分支（**可选**，写较大改动时用），如 `feature/pantry-card-list` |

### 8.2 日常流程（2026-09-11 决议：直推 dev，免 PR）

1. 开工前 `git checkout dev && git pull`，直接在 `dev` 最新状态上开工；
2. 改动用 Conventional Commits（`feat(pantry): …` / `fix(recipe): …` / `docs: …`）提交后**直接 push 到 `dev`**，不强制开 PR —— 这是给课程小队的轻量化选择；
3. 组长从 W3 起持续对 `dev` 的新改动做 Code Review（能跑、合接口、无 UI 违规），发现问题在群里沟通修改，不卡合并；
4. 每个里程碑验收通过后，**仅由组长**将 `dev` 合入 `main` 并打 tag（组员不直推 `main`，保护"稳定版可跑"底线）；
5. 若 `dev` 频繁被弄崩、改动互相踩踏，再恢复 PR 把关。

### 8.3 红线

- ❌ 不直接提交 `main`（`dev` 可直推，见 8.2）；
- ❌ 不用 `git push --force`；
- ❌ 不提交密钥、密码、`.env`；
- ❌ 不提交超过几十 MB 的大文件；
- ❌ 冲突标记（`<<<<<<<`）没清干净就提交；
- ❌ 改共享区不打 `[shared]` 不同步。
