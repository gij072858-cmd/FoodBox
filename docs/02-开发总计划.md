## 一、项目概况与目标

**双目标对应两期结构：**

1. **期1 = 第一目标（W1–W8，8 周，底线）**：完成软件工程课程作业——软件开发计划、需求分析、概要设计、详细设计、测试五份文档齐全，App 核心链路可演示，通过答辩。期1 范围 = 核心链路（库 / 菜式 / 时序含倒推与拖拽 / 我的 XP 体系 / 动态占位）+ 期1 功能包：**F1 购物清单、F2 份量换算、F3 临期提醒、F4 悬浮计时条、F6 数据导出备份、F12 时令推荐（简易版）、F14 复盘笔记、F8 步骤术语解释**。
2. **期2 = 第二目标（后续升级，追求）**：期1 v1.0 发布后的长期迭代，做成真正能用、长期维护的产品——上云（Supabase + 账号体系）、社区（动态真实化 + 宣传运营）、锦上添花（F5 深色模式、F7 成就、F8 引导模式、F10 营养粗估、F11 语音播报、F13 桌面小组件、F15 剩食材搜索、F18 无障碍）。版本列车与分版本分工详见第十一章。

**核心指标：**

- 核心链路全通：录入食材 → 推荐菜式 → 加入时序 → 排程执行 → 倒计时引导 → 扣减库存 → 打卡记录；
- 初始内容：预置食材/调料 200+ 条、官方菜式 30–50 道（步骤带耗时）；
- 双端可跑：安卓 App + Windows 桌面端；
- 设计还原度：严格执行《01-食匣详细构想》第一章设计规范。

## 三、技术架构决策

| 决策项 | 定案 | 理由 |
|---|---|---|
| 框架 | **Flutter（Dart）** | 一套代码产出安卓 + Windows 双端；声明式 UI 适合实现精美设计；团队统一学一门语言 |
| 状态管理 | **Riverpod**（可替换） | 编译期安全、测试友好、社区主流 |
| 本地数据库 | **Drift（SQLite）**（可替换） | 类型安全的 SQL 封装，支撑库/菜式/时序的结构化数据 |
| 后端 | **期1 无服务端**：Repository 接口层隔离数据访问，预留 Supabase 云实现（期2 动态上线时启用） | 8 周期1 内规避后端风险，架构不留债 |
| 扫码 | mobile_scanner 插件（安卓端）；电脑端降级为手动输入条码 | — |
| 倒计时 | **结束时间戳方案**：不依赖 Timer 周期计数，记录结束时刻、每帧按时间差渲染；本地通知用 flutter_local_notifications 兜底 | 从根上解决后台挂起恢复、多倒计时并行的漂移问题 |
| 路由 | go_router | 声明式路由，双端一致 |
| 图片 | 真实高清图优先导入（小范围使用）+ 缺图 AI 生成统一风格兜底 + 用户自拍；资源目录可整体替换，版式与图解耦 | 按组长修订的策略，见构想文档第四章 |

**代码结构约定**（mono-repo）：

```
FoodBox/
├── app/                    # Flutter 工程
│   ├── lib/
│   │   ├── core/           # 主题常量、路由、工具
│   │   ├── data/           # Drift 数据库、Repository 接口与本地实现
│   │   ├── features/
│   │   │   ├── pantry/     # 库（成员二）
│   │   │   ├── recipe/     # 菜式（成员三）
│   │   │   ├── schedule/   # 时序（组长）
│   │   │   ├── feed/       # 动态占位（成员四）
│   │   │   └── profile/    # 我的（成员四）
│   │   └── widgets/        # 公共组件库（成员四）
│   └── assets/             # 预置图片、食材基础库 JSON、菜式数据 JSON
└── docs/                   # 全部文档
```

## 五、逐周详细计划

### W1 — 地基周：环境、脚手架、文档启动

- **共同任务**：安装 Flutter 开发环境（组长提供图文环境指南，统一版本）；每人跑通"Hello FoodBox"；注册/配置 GitHub 并完成首次提交。
- **组长**：创建仓库与分支模型；搭建脚手架——go_router 路由骨架、Theme 常量接入、Drift 数据库与六张表（Item/Recipe/Step/ScheduleItem/Record/Profile，口径见本文第七章与《接口约定.md》）、Repository 接口层定义；底部 TabBar + 首页顶部三 Tab 空页面框架。
- **成员二**：Dart 语言学习（清单见任务书）；开始整理食材/调料基础数据（名称、分类、默认保质期、存放位置、简介四段）。
- **成员三**：Dart 语言学习；收集 30–50 道目标菜式清单并定格式模板。
- **成员四**：把《01-食匣详细构想》1.3 设计规范（v2.0 Apple 毛玻璃）翻译为 Flutter Theme，输出 `core/theme.dart`；完成 `widgets/` 下 `Fb*` 公共组件库 + `showcase_page` 走查页（已合入 dev）。
- **文档**：组长主笔《软件开发计划》v1；《需求分析》启动（全组周五开 1 小时需求确认会，逐条过歧义清单结论）。
- **验收**：双端空壳可运行；设计系统 v2.0 组件库 + showcase 页合入 dev；四人均完成首次提交（直推 dev，见 §6.5）。

## 六、协作与沟通机制

### 6.1 沟通渠道分层

### 6.5 Git 与 GitHub 工作流

> 本节是规则约定；逐步操作细则（含命令与翻车自救）见《docs/GitHub协作指南.md》，全组开工前必读。

**分支模型**：

- `main`：**受保护，仅组长可合并**；每个里程碑打 tag（v0.1 … v1.0）。始终保持在"验收通过即可跑"状态。
- `dev`：**集成分支，全组直接 push（免 PR）**；每晚保持可运行状态。
- `feature/<模块>-<简述>`：个人功能分支（可选）。写较大改动时可开，但**合并回 dev 不需要 PR，组长确认后 `squash` 合并即可**。

**日常流程（2026-09-11 决议：直推 dev，免 PR）**：

1. 大部分改动直接从 `dev` 当前状态开工，提交用 Conventional Commits（`feat(pantry): …` / `fix(recipe): …` / `docs: …`）；
2. **直接 `push` 到 dev**（就近拉取、提交、推送），不强制开 PR——这是给课程小队的轻量化选择，减少流程负担；
3. 组长在 W3 起持续对 dev 的新改动做 Code Review（能跑、合接口、无 UI 违规），发现问题及时在群里沟通修改，不卡合并；
4. **里程碑验收通过后，仅由组长将 `dev` 合入 `main` 并打 tag**；组员不直推 main，保护"稳定版可跑"底线。

**共享区纪律（不分 PR / 直推都适用）**：`core/`、`data/`、`widgets/`、`接口约定.md` 是共享区——**改动共享区文件必须在提交说明加 `[shared]` 并在群里同步一句**；各人模块目录内自由改动。

**何时升级回 PR**：若 dev 频繁被弄崩、改动互相踩踏，再恢复 PR 把关。

**GitHub 宣传（W8 启动）**：README 含截图 GIF、功能列表、安装包 Release；后续动态功能上线时发一次 v2.0 宣传。

### 6.6 决策与分歧裁决

- 技术与接口分歧：组内讨论 → **组长裁决**（架构、接口、排期）；纯视觉规范分歧由**成员四裁决**（设计规范守护者）；裁决结果记入提交说明或 issue 留痕；
- 任务认领以意愿优先、模块延续为辅；无人认领的任务由组长按剩余负荷指派。

## 七、接口约定机制

**原则：先定接口，后写实现。** W1 由组长在《概要设计》骨架中冻结以下约定，存于 `docs/接口约定.md`（W1 内创建）：

1. **数据模型**：Item / Recipe / Step / ScheduleItem / Record / Profile 六张表的字段（以构想文档附录为准，概要设计细化）；
2. **Repository 接口**：每个模块只允许通过接口访问数据，禁止直接操作数据库；
3. **跨模块调用契约**：
   - 库 → 菜式：`PantryRepository.watchAll()` 提供库存流；推荐算法由组长实现为 `RecipeMatcher.match(recipes, items)`；
   - 菜式 → 时序：`ScheduleRepository.add(recipeId)`；长按浮层只调接口不关心实现；
   - 时序 → 库：执行完成回调 `PantryRepository.consume(recipeId)`；
   - 倒计时组件：成员四提供水平倒计时条公共组件（`widgets/` 内，命名统一 `Fb` 前缀），成员三与组长直接使用，不重写。
4. **接口变更流程**：发起人在群里提变更 → 组长裁决 → 更新 `接口约定.md` → 相关方确认后才改代码。

## 九、质量检测与拼接流程

**质量三关：**

1. **Code Review 关**（随时）：组长 Review——能跑、符合接口约定、无明显 UI 违规；
2. **走查关**（W3/W7）：成员四对照设计规范逐页走查，问题录为 issue，限期清零；
3. **验收关**（每周末）：对照当周里程碑逐条演示确认，录屏存档。

**拼接流程（W7）**：

1. 周一：全员将功能分支合入 `dev`，解决冲突（组长主导，双人结对处理共享区冲突）；
2. 周二至周三：核心链路 + 边界场景联调（清单：空库状态、无菜式可推荐、倒计时后台恢复、库关闭模式、双端布局）；
3. 周四：性能与流畅度优化；双端打包；
4. 周五：功能冻结，全量回归。

**验收标准（v1.0）：**

- 功能：核心链路五环节（录食材→推荐→排程→执行→扣库存）无阻断性 bug；
- 流畅：列表滚动与转场无明显掉帧（目标 60fps，演示机实测）；
- 设计：走查 issue 清零，关键页面（库/菜式详情/时序执行）达到设计规范 95% 还原；
- 文档：五份课程文档与代码一致。
