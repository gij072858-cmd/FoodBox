# 食材 / 调料整理表 —— 填写说明与口径（W1 交付物 · 成员二）

> **对应任务**：成员二任务书 A 段「整理食材/调料基础库 JSON（≥200 条）」；W1 关键交付＝**数据整理表模板**。
> **唯一数据源**：`docs/数据/食材调料整理表模板.csv`
> **最终产物**：`app/assets/data/food_items.json`（由整理表生成，不手工改）

---

## 一、四步工作流

```
① 填表  →  ② 生成  →  ③ 校验  →  ④ 提交
```

```bash
# ② 整理表 → food_items.json
cd app
dart run tool/import_food_items.dart

# ③ 字段完整性校验（组长交付的关卡，必须全绿）
dart run tool/validate_assets.dart
```

1. **填表**：用 Excel / WPS 打开 `docs/数据/食材调料整理表模板.csv`，在 5 条样例行下面继续追加。表头不要改、不要删列。
2. **保存**：**必须另存为「CSV UTF-8（逗号分隔）」**。存成普通的「CSV（逗号分隔）」会变成 GBK，中文全乱，导入脚本会直接报错拒收。
3. **生成**：跑上面第 ② 步，脚本逐行检查后覆盖写 `app/assets/data/food_items.json`。
4. **校验 + 提交**：跑第 ③ 步确认通过，再按约定提交（`[shared]` 仅共享区改动才加，本任务只动 `assets/data/` 与 `docs/数据/`，**不加** `[shared]`）。

> **约定（请组长确认）**：`food_items.json` 转为**生成物**——以后改数据一律改整理表再重新生成，不再手工编辑 JSON。这样 200+ 条才不会出现「表和 JSON 两份不一致」。

## 二、列口径（11 列，与 JSON 字段 1:1）

| 列名 | 必填 | 取值 | 说明 |
|---|---|---|---|
| `name` | ✅ | 中文标准名，1–60 字 | **用最通用的标准名**（「番茄」不用「西红柿」）。别名不写在这里，走组长的 `alias_map.json` |
| `category` | ✅ | 见第三章 11 个分类 | 自由文本，但**只能从第三章的分类里选**，否则卡片配色取不到 |
| `kind` | ✅ | `ingredient` / `seasoning` | 食材 / 调料。**写英文枚举名，不写「食材」** |
| `shelfLifeDays` | ✅ | 正整数（天数） | **按 `storageLocation` 所指环境**的默认保质期，不是最长可存天数 |
| `storageLocation` | ✅ | `fridge` / `freezer` / `room` | 冷藏 / 冷冻 / 常温。**写英文枚举名，不写「冷藏」** |
| `opened` | ⬜ | `true` / `false`，留空＝未开封 | 仅调料有意义。**预置库绝大多数行留空**，这是用户入库后的状态 |
| `barcode` | ⬜ | 纯数字字符串 | 扫码自学习的种子数据，只填**你手头真有**的常见包装品条码；留空完全没问题 |
| `introWhat` | ✅ | 一句话，20–45 字 | 【是什么】是什么、风味特点 |
| `introHow` | ✅ | 一句话，20–45 字 | 【怎么用】常见用法、适合搭配 |
| `introStore` | ✅ | 一句话，20–45 字 | 【怎么存】存放方式 + 保质期参考 |
| `introTip` | ✅ | 一句话，20–45 字 | 【小贴士】挑选/处理冷知识 |

**四段简介的必填口径**：构想 2.2.4 把「小贴士」写成"可选"，但 W1 冻结的校验脚本对四段一律要求非空 —— **以校验脚本为准，四段都要写**。反过来说，这也是好事：200 条全库调性统一，详情页不会有的有贴士有的空着。

## 五、默认保质期参考档位（`shelfLifeDays`）

填的是**该条默认存放环境下的保质期**（不是最长）。表里给的是常见区间，具体条目按常识取整数值即可。

| 存放位置 | 典型区间 | 例子 |
|---|---|---|
| `room` 常温 | 葱姜蒜 30–60；米面杂粮 180–365；干货 180–540；酱油醋类 540–720；盐糖 730+ | 蒜 60、生抽 540、大米 365 |
| `fridge` 冷藏 | 叶菜 3–7；瓜茄根茎 7–14；鲜肉 1–3；鲜水产 1–2；蛋 30–45；豆制品 3–7；开封调料 90–180 | 番茄 5、鸡腿 2、鸡蛋 30 |
| `freezer` 冷冻 | 生肉 90–180；水产 90–180；面点 60–180 | 冷冻虾仁 120、速冻饺子 90 |

> 存疑就**宁可取保守值**（短一点）。任务书原话：「宁慢勿错」——用户按提示买回来早几天吃完，比按提示吃到过期的体验好得多。
>
> 「按存放位置校正」属于 W4 的录入功能（Q3-C），整理表只填**默认环境**下的一个数。

## 六、简介四段写法

固定四段、固定顺序，全库调性一致。**每段一句话，不换行、不分点、不用 markdown**（卡片里是纯文本渲染，换行会把卡片撑高）。

**正例**（直接照这个手感写）：

| 字段 | 内容 |
|---|---|
| `introWhat` | 茄科蔬果，酸甜多汁，富含番茄红素与维生素C，是家常菜里出场率最高的食材之一。 |
| `introHow` | 可生吃、炒食、炖汤；炒制时先用热油煸出红油再下其他食材，酸甜味更浓。 |
| `introStore` | 未熟透的番茄常温催熟，已熟的放冷藏并尽快食用；冷藏后风味略减，烹饪用无妨。 |
| `introTip` | 顶部划十字烫开水可轻松去皮；与鸡蛋同炒是先炒蛋再下番茄，顺序反了容易出水。 |

**反例**（会被打回重写）：

| 反面写法 | 问题 |
|---|---|
| 「番茄很好吃，可以做很多菜」 | 空话，没有信息量，200 条这样写详情页就是废页 |
| 「详见附录 A」/「略」 | 占位符，四段必须写实 |
| 一段里塞三段内容、用 `1. 2. 3.` 分点 | 段位串了；`introHow` 只讲用法，存放另起 `introStore` |
| 「本品富含多种营养物质，具有增强免疫力的功效」 | 保健品式宣传，涉及功效宣称，删掉 |
| 描述里带真实品牌名（「海天金标生抽」） | 品牌是用户入库时填的字段，预置库写通用名 |

**工作节奏建议**：先按第四章的起步池把 226 条的 `name / category / kind / shelfLifeDays / storageLocation` 快速铺一遍（这五列靠常识，快）；再按分类批量写四段简介（同一分类的「怎么存」句式高度相似，批量写效率高）。**不要一条条写完整行**，否则前 20 条精致、后 180 条糊弄。

## 七、校验脚本会拦下的 7 类常见错误

| # | 错误 | 正确写法 |
|---|---|---|
| 1 | `kind` 写了中文「食材」 | `ingredient` |
| 2 | `storageLocation` 写了「冷藏」 | `fridge`（冷藏）/ `freezer`（冷冻）/ `room`（常温） |
| 3 | `shelfLifeDays` 写了「约7天」、`0`、负数 | 正整数 `7` |
| 4 | 四段简介里有空段 | 四段全填（含 `introTip`） |
| 5 | 同一名称出现两次 | 合并成一条；**别名写法（西红柿 vs 番茄）也算重复**——只留标准名，别名交给 `alias_map.json` |
| 6 | 字段里用了半角逗号导致列错位 | 半角逗号一律换成中文顿号「、」或全角逗号「，」；或给整个单元格加引号 |
| 7 | 简介里手动换行 | 一条一段，不换行 |

## 八、配图与缺图清单

图片**不写进整理表、也不写进 `food_items.json`**（`image_path` 是用户入库后的字段）。预置图走 `app/assets/images/`，由 `image_path` 约定路径引用，目录设计为可整体替换（构想 407：「图可换、版式不动」）。

配图策略（构想 407 决案）：

1. **真实高清图优先** —— 高频食材/调料先收真实图，小范围使用不涉版权；
2. 收不到的用 **AI 生成统一风格图**兜底（构图、光线、背景统一）；
3. 用户条目允许自拍上传；
4. **收集不到的实时记进缺图清单**（下表），W2–W4 按批补。

**缺图清单**（边填表边追加，别攒到最后）：

| 条目名 | 分类 | 状态 | 备注（候选来源 / 待补原因） |
|---|---|---|---|
| 例：竹荪 | 菌菇干货 | 待补 | 常见图源风格不统一，走 AI 兜底 |
| | | | |

状态取值：`真实图已收` / `AI 兜底` / `待补`。

## 九、纪律

- **`app/assets/data/` 属共享区**（先例：`26d53d6 [shared] docs: alias_map.json 结构定义与骨架`），改动 `food_items.json` 提交说明**必须加 `[shared]`** 并在群里同步；`tools/`、`docs/数据/` 不算共享区；
- 不碰 `core/` / `data/` / `widgets/` 下的任何文件；
- 提交信息按 Conventional Commits，建议 `[shared] data(pantry): 食材基础库扩充至 N 条`；
- 数据口径有歧义（比如某食材到底算蔬菜还是调料）**在群里问一句再写**，不要自己猜了往下写——200 条的返工成本很高；
- 本文件是整理表的口径依据；口径变更先改本文件再改数据。
